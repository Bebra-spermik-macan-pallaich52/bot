# Crypto Pattern Lab

Исследовательская система сбора и анализа публичных минутных свечей Bybit.
Ордеров, приватных API и подключения реальной торговли нет.

## Архитектура

- `collector.py`: WebSocket → только подтверждённые закрытые свечи → PostgreSQL.
  При ошибках транспорта/записи — переподключение с ограниченным exponential
  backoff и jitter. Application heartbeat Bybit + WebSocket ping/pong;
  watchdog переподключает поток без свежих закрытых свечей более 180 секунд.
- `backfill.py` / `bybit.py`: REST-восстановление, ограниченные повторы timeout,
  429/5xx и временных кодов Bybit. Проверка каждой ожидаемой минуты страницы;
  пустая/неполная страница не считается успешной. Постоянный HTTP 403 не скрывается.
- При старте — восстановление `BACKFILL_DAYS` (1–90), затем последние 10 минут
  каждую минуту и полное окно раз в час. Страницы обрабатываются от новых к старым,
  фиксируются отдельно и безопасно повторяются. Долгие простои восстанавливаются
  в пределах окна; более старые пропуски автоматически не исправляются.
- `storage.py`: единая схема и UPSERT по exchange/category/symbol/interval/start_ms.
  Проверка OHLCV, минутной сетки и конечности чисел; сериализация стартового DDL.
- `analysis.py`: признаки → выбор повторяющегося условия на train → test → JSON.
- `health.py`: проверка 10 последовательных недавних свечей с задержкой 2 минуты
  и свежести отчёта аналитика. Backfill отдельно проверяет время последней
  успешной REST-дозагрузки и полного восстановления; свежий WebSocket их не маскирует.
  Отсутствие данных означает нездоровый сбор.

WebSocket и REST пишут в одну таблицу; REST восстанавливает сообщения,
которые не удалось записать. Гарантия полноты зависит от доступности REST Bybit,
срока хранения окна, часов сервера и даты листинга инструмента.

## Запуск

Docker Engine с Compose v2 на Linux-сервере либо Docker Desktop на компьютере.
Серверу нужны HTTPS/WSS к `api.bybit.com` и `stream.bybit.com`, точное время/NTP,
диск для PostgreSQL и резервных копий. PostgreSQL наружу не публикуется.

```bash
cp .env.example .env
# Задайте собственный длинный DB_PASSWORD в .env; не публикуйте этот файл.
docker compose config -q
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 collector backfill analyst
```

PowerShell: вместо `cp` можно использовать `Copy-Item .env.example .env`.
Отчёт: `docker compose exec -T analyst cat /app/reports/latest.json`.
Число свечей:

```bash
docker compose exec -T db psql -U market -d market -c 'SELECT count(*) FROM candles;'
```

Данные сохраняются в именованных volumes `pgdata`, `reports`, `ingestion_state` и `forecast_state`.
При обновлении сохраняйте исходную директорию/Compose project name;
иначе Docker создаст другие volumes. `docker compose down` сохраняет данные.
`down -v` удаляет volumes — для обычной остановки его не используйте.
Смена пароля в `.env` не меняет пароль уже существующей базы.

Для разработки без Docker: Python 3.12, `python -m venv .venv`, затем
`.venv/bin/python -m pip install -r requirements-dev.lock` (Windows:
`.venv\Scripts\python`). Задайте `DATABASE_URL` или `PGHOST`, `PGDATABASE`,
`PGUSER`, `DB_PASSWORD` и запускайте три worker-скрипта отдельно.
Переменные из `.env` читает Compose; Python самостоятельно этот файл не загружает.

В управляемой облачной среде: `bash scripts/setup.sh` создаёт venv вне checkout
и `.env` со случайным локальным паролем только при отсутствии файла.
Для Docker используйте `-f compose.yaml -f compose.cloud.yaml`,
`BUILDX_CONFIG=/workspace/buildx`. Cloud override передаёт системный CA bundle
через BuildKit secret и read-only runtime mount. TLS остаётся включённым.
Облачная сессия для разработки не заменяет постоянно включённый сервер.

## Веб-панель состояния

После `docker compose up -d --build` откройте **http://127.0.0.1:8080**
в браузере на компьютере, где запущен Docker. Панель обновляется каждые 15 секунд.
Изменить локальный порт можно через `DASHBOARD_PORT` в `.env`.

Панель показывает:

- Доступность PostgreSQL и поступление новых закрытых свечей. Это проверка
  записанных данных, а не состояния контейнера или самого WebSocket-соединения.
- Последнюю успешную REST-дозагрузку/полное восстановление, текущую фазу и
  безопасную категорию последней ошибки (HTTP 403, HTTP 429, сеть, БД и др.).
- Число свечей, покрытие заданного окна `BACKFILL_DAYS`, пропущенные минуты,
  дневное покрытие и диапазоны пропусков, включая начало и конец окна.
- Некорректные OHLCV в окне, свечи вне минутной сетки и незакрытые/будущие записи.
- Свежесть отчёта аналитика и тестовые результаты паттернов: события, среднее,
  доверительный интервал и чувствительность к затратам. Преимущество не заявляется.

Окно проверки — последние `BACKFILL_DAYS`, а не только участок между первой
и последней имеющейся свечой. Поэтому у нового или недавно залистившегося
инструмента будут видны отсутствующие исторические минуты. Последние две
закрытые минуты выделяются как ожидающие доставки; они не делают весь аудит
неуспешным, если остальные проверки пройдены. На границе UTC-дня учитываются
только минуты, попавшие в окно. Дубликаты времени запрещены первичным ключом БД.

При недоступной БД состояние неизвестно; при потере соединения браузер явно
помечает последние данные как устаревшие. REST-ошибка не маскируется работающим
WebSocket. Запросы к БД выполняются в read-only snapshot с statement timeout;
результат кешируется на 15 секунд в каждом процессе сервера.

Панель работает через Gunicorn, не подключает Docker socket и не предоставляет
операций записи. Отчёты и состояние подключены через read-only volumes.
Порт публикуется только на `127.0.0.1`. Для сервера используйте SSH-туннель,
например `ssh -L 8080:127.0.0.1:8080 user@server`, затем откройте тот же локальный
адрес. Встроенного входа по паролю в панель нет.

API:

- `GET /api/status` — текущие данные качества и компонентов. При недоступной БД
  возвращает JSON с `database.state=unavailable`, остальные компоненты сохраняются.
- `GET /healthz` — сервер панели отвечает. Docker healthcheck проверяет именно это;
  здоровый dashboard-контейнер не означает полноценность рыночной истории.
- `GET /readyz` — HTTP 200 только когда качество истории, REST и аналитик готовы,
  иначе HTTP 503 с данными состояния.

### Обновление установки из ZIP на Windows

1. Скачайте свежий ZIP из GitHub: **Code → Download ZIP**.
2. Скопируйте файлы проекта в **ту же папку**, из которой ранее запускали Compose,
   с заменой исходников. Сохраните свой `.env`; не заменяйте его файлом примера.
3. В PowerShell в этой папке выполните `docker compose up -d --build`.
4. Откройте http://127.0.0.1:8080. Если порт занят, задайте `DASHBOARD_PORT=8081`
   в `.env`, повторите команду запуска и откройте порт 8081.

Git для такого обновления не требуется. Существующая PostgreSQL остаётся в прежнем
volume при сохранении Compose project name. Не используйте `down -v`.

## Прогноз конечной цены через 10 минут

Новый сервис `forecaster` вычисляет экспериментальные вероятности по закрытым
минутным свечам. Например, для свечи с началом 10:00 UTC исходная цена известна
после закрытия в 10:01, целевая цена — закрытие в 10:11. Это прогноз конечного
изменения, не траектория графика и не гарантия движения.

После обновления файлов в прежней папке, сохранив `.env` и project name:

```bash
docker compose up -d --build
docker compose logs --tail=50 forecaster
```

В верхней части панели появятся вероятности падения / небольшого изменения /
роста, исходная цена, оценка среднего конечного изменения и описательный
диапазон. Границы по умолчанию ±0,10% (`FORECAST_BAND_BPS=10`): падение строго
ниже −0,10%, рост строго выше +0,10%, всё внутри — небольшой ход.
Это определения классов, не торговые уровни. Диапазон между 10-м и 90-м
процентилями строится по прошлым исходам; фактическое покрытие на test показано
отдельно и не обязано равняться 80%.

### Обучение и историческая проверка

Фиксированная logistic regression со StandardScaler использует только прошлые
изменения цены за 1/3/5/10/30/60 минут, волатильность, относительный объём,
диапазон/тело свечи и положение цены относительно прошлых high/low.
При пропуске или некорректных данных в недавнем 60-минутном окне прогноз
не публикуется. Последние свечи без будущего исхода используются только для
текущего прогноза, не для обучения.

Из 30 обучающих дней первые 25 используются для модели и масштаба признаков,
следующие 5 — для temperature calibration. Температура выбирается из фиксированного
набора только по этим прошлым данным. На обеих границах исключаются события,
чей исход закрывается на границе следующего периода или позже.
Случайного перемешивания train/test нет.

Далее идут 10 дней test, окно сдвигается на 10 дней, модель обучается заново на
прошлом. Для ≥3 полных периодов нужно около 60–61 дней; 90 дней обычно дают 5–6
периодов в зависимости от UTC-границ и пропусков. Недостаток истории/примеров
класса означает ожидание или пропущенный период, без выдуманных вероятностей.

Проверка использует исходные свечи на фиксированной UTC-сетке с шагом 10 минут:
десятиминутные доходности не перекрываются, хотя соседние наблюдения могут зависеть.
Log loss/Brier сравнивают вероятности с частотами классов на прошлом; accuracy —
с выбором самого частого класса. Высокая accuracy может означать лишь частый
выбор небольшого изменения. Для среднего изменения есть MAE против нулевого
изменения; для диапазона — фактическое покрытие. JSON также содержит balanced
accuracy и калибровочные группы.

Bootstrap по UTC-дням оценивает разницу log loss с базой. Даже если CI выше нуля,
Brier лучше и есть ≥3 периода, результат только предварительный исторический.
Нет поправки на все исследовательские попытки; нужен новый будущий контроль.
Отсутствие преимущества явно указано рядом с вероятностями.

Среднее и диапазон — смесь исторических распределений классов с модельными
весами. Это приближение, не доказанный условный доверительный интервал.
Новости, ликвидность, смена режима, funding и реальные исполнения не моделируются.
Калибровка вероятностей, прогнозное преимущество и прибыльность не гарантируются.

### Проверка новых прогнозов

Модель обновляется примерно раз в час, расчёт — раз в минуту. Отчёт
`reports/forecast.json` и собственный доверенный cache в `forecast_state`
сохраняются в volumes. Историческая проверка обновляется до раз в 6 часов,
на новом UTC-дне или после существенной дозагрузки. Повторное изучение этой
истории остаётся исследованием, не новым независимым тестом.

Таблица PostgreSQL `forecasts` записывает прогноз до исхода: время публикации,
протокол, model ID, исходную цену, вероятности, диапазон и базовые вероятности.
Перед записью свеча должна быть закрыта и не старше 90 секунд; долгий расчёт
перепроверяет часы. `ON CONFLICT DO NOTHING` запрещает замену прогноза того же
протокола/инструмента/времени; панель получает именно сохранённый вариант.
Это ограничение приложения, не защита от владельца БД.

После наступления цели исход сопоставляется с закрытой целевой свечой.
До её появления результат не оценивается. Общая оценка берёт максимум 10000
последних завершённых исходов данного протокола на той же десятиминутной сетке.
Частые минутные прогнозы остаются в журнале, но не раздувают размер теста.
Смена порога создаёт другой протокол; группы не смешиваются. При изменении
модели/признаков разработчик должен обновить версию в `forecasting.py`.

Истёкший прогноз, устаревший отчёт или недоступная БД не отображаются как
актуальные вероятности. Healthcheck forecaster проверяет свежесть отчёта процесса,
не качество предсказаний. `/readyz` по-прежнему относится к сбору/истории и
аналитике; модель передаётся отдельно в `forecast` внутри `/api/status`.

Существующий pg_dump-скрипт включает журнал. Сохраняйте volumes для будущей
проверки. Не загружайте чужие `.joblib`/pickle: worker читает только свой
доверенный cache. Биржевых API-ключей, ордеров и реальной торговли нет.

## Признаки и историческая проверка

Доступны отношение объёма к медиане предыдущих 60 свечей, изменение цены за
15 минут, волатильность за 60 минут, диапазон свечи и пробой предыдущего high/low.
Текущая свеча используется только после закрытия. Пропуск в прошлом окне
делает признаки недоступными; пропуск между событием и будущим исходом
делает конкретный исход недоступным. Окна 15/60 минут оцениваются отдельно.

Для каждого направления рассматриваются заранее заданные пороги объёма
1.5/2/3. Выбирается порог с наибольшим train excess mean для 60 минут,
если на train есть `MIN_EVENTS` событий. События одного направления разделены
минимум 60 минутами. Это небольшая семья шаблонов, а не универсальный ML-поиск.

По умолчанию используется хронологический split 70/30. Train-события исключаются,
если их 60-минутный исход закрывается на границе test или позже. Test может
использовать прошлые train-свечи для признаков — они уже известны к моменту события.
Изменение test-цен не влияет на выбор порога и train-статистику.

Перед подтверждающим экспериментом установите `TEST_START_MS` (UTC Unix ms)
и зафиксируйте исследовательский протокол **до просмотра test-результатов**.
Повторное изучение test и подбор кода по нему делает его частью исследования;
потребуется новый будущий период проверки. Автоматическое 70/30 — разведочный
режим, не новый независимый holdout при каждом запуске. Для фиксированной границы
должна сохраняться достаточная история; текущий SELECT ограничен 130000 свечами.

JSON содержит train/test отдельно, размер выборки, среднюю направленную доходность
цены, долю положительных изменений, описательный all-bar baseline, excess mean
и чувствительность к round-trip costs (`COST_BPS`, по умолчанию 10 б.п.).
Для DOWN направление равно минусу изменения цены, а не точной доходности short.
Bootstrap по UTC-дням даёт описательный 95% CI среднего при наличии ≥5 дней.
Это не скорректированная проверка превышения baseline и не доказательство значимости.

`MIN_EVENTS=30` — нижняя граница вывода статистики, не гарантия мощности или
преимущества. All-bar baseline не является независимым подобранным контролем.
Нет поправки на множество исследовательских попыток, внешние факторы,
funding, реальные исполнения и полноценный slippage. Прибыльность не установлена.

## Тесты

Быстрые тесты (интеграционные явно пропускаются без отдельной тестовой БД):

```bash
python -m pytest -q
```

Полный набор, включая реальный PostgreSQL, в изолированном временном стеке:

```bash
bash scripts/test.sh
```

Либо в PowerShell:

```powershell
docker compose -p crypto-pattern-lab-tests -f compose.test.yaml up --build --abort-on-container-exit --exit-code-from tests
docker compose -p crypto-pattern-lab-tests -f compose.test.yaml down
```

Тестовая БД не публикует порты, хранится в tmpfs и не использует production volumes.
Для pytest с внешней тестовой БД задайте `TEST_DATABASE_URL`; имя БД обязано
заканчиваться на `_test`. Тесты очищают её таблицу candles. Production URL не задавайте.
В managed cloud: `BUILDX_CONFIG=/workspace/buildx CPL_TEST_OVERRIDE="$PWD/compose.cloud.test.yaml" bash scripts/test.sh`.

Покрытие: будущие данные/prefix invariance, purge на границе split, пропуски,
порядок и дубли, исходы UP/DOWN, insufficient sample, bounded retries,
ошибки WebSocket/БД, reconnect, повторное восстановление пропуска, UPSERT,
конкурентный старт схемы и генерация отчёта из настоящей БД.
Данные функциональных тестов синтетические, не доказательство рыночной закономерности.

## Эксплуатация 24/7 на Linux

- Включите автозапуск Docker: `sudo systemctl enable --now docker`.
  Workers имеют `restart: unless-stopped`, ограничение логов, непривилегированного
  пользователя, read-only root filesystem и обработку SIGTERM.
- Настройте внешний мониторинг `docker compose ps`, disk usage, healthcheck,
  времени последней свечи, успешности бэкапов и синхронизации времени.
  Docker healthcheck сам по себе не перезапускает unhealthy-контейнер;
  restart policy применяется к завершившимся процессам. Автоматические алерты
  здесь ещё не подключены.
- Ежедневно: `bash scripts/backup.sh`; например cron от пользователя с Docker:
  `15 3 * * * cd /srv/crypto-pattern-lab && bash scripts/backup.sh >> backups-cron.log 2>&1`.
  Настройте ротацию этого host-лога, retention, шифрование и копию вне сервера отдельно.
- Проверяйте восстановление: `bash scripts/restore-check.sh backups/<имя>.dump`.
  Скрипт создаёт отдельную `restore_test`, отказывается перезаписывать существующую
  базу с таким именем, восстанавливает дамп и удаляет только созданную им тестовую БД.
- Сначала проверяйте обновления на копии; архивируйте текущие `.env` и volumes
  безопасным способом. Не включайте секреты и дампы в Git или общие архивы.

## Состояние проверки в облачной сессии

См. `VALIDATION.md`: отдельно указаны локальные тесты, сборка контейнеров,
проверка PostgreSQL и блокировка живого доступа к Bybit. Настройка внешнего
мониторинга/бэкапов на вашем сервере и длительная проверка 24/7 ещё требуются.

Опциональная проверка интерфейса настоящим Chromium:
`node scripts/check-dashboard.cjs` при установленном Playwright и браузере.
`CHROMIUM_PATH` задаёт путь к системному Chromium, `PLAYWRIGHT_MODULE` — путь
к модулю Playwright при установке вне node_modules, `CPL_DASHBOARD_URL` — адрес
запущенной панели. Скрипт проверяет реальную загрузку страницы и API, а состояния
ошибки, восстановления и тестовую таблицу — через перехват ответов браузером;
данные PostgreSQL не меняет. Это отдельная проверка, не часть pytest/GitHub Actions.
